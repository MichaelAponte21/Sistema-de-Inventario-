**Fecha:** 2026-05-08  
**Version:** Sprint 2 + Mejoras

## 1. Que hace el sistema

El Sistema de Inventario Web es una aplicacion web de tres capas (base de datos, backend, frontend) disenada para comercios que necesitan:

- Saber cuantas unidades tienen de cada producto y donde estan al limite de reabastecimiento
- Procesar ventas en el mostrador registrando el metodo de pago y el cajero
- Cuadrar la caja al final del turno comparando el efectivo esperado con el real
- Consultar reportes de ventas del dia, semana y mes sin usar Excel
- Controlar que cada empleado solo pueda hacer lo que le corresponde (permisos)

## 2. Arquitectura General

```
Navegador (React SPA)
      |
      | HTTP + JWT
      v
Backend REST (Spring Boot)   ←→   Base de Datos (PostgreSQL)
      |
      | Docker Network
      v
docker-compose.yml orquesta los tres servicios
```

### Flujo de una peticion tipica

1. El navegador envia `GET /api/productos` con el token JWT en el header `Authorization: Bearer <token>`.
2. El filtro `JwtAuthenticationFilter` intercepta la peticion, valida el token y establece el contexto de seguridad con el usuario y sus permisos.
3. Spring Security verifica que el endpoint permita el rol/permiso del usuario.
4. El `ProductoController` delega al `ProductoService`.
5. El servicio consulta la BD via `ProductoRepository` (Spring Data JPA).
6. La respuesta viaja de vuelta como JSON.
7. TanStack Query en el frontend cachea el resultado y re-renderiza los componentes.

## 3. Capa de Base de Datos

### Motor y configuracion

- **PostgreSQL 16** corriendo en Docker, puerto externo `7000`
- Hibernate con `ddl-auto=update`: al arrancar el backend, crea o modifica tablas automaticamente segun las entidades JPA
- Todas las columnas `id` son `GENERATED BY DEFAULT AS IDENTITY` (equivalente a autoincrement seguro)

### Tablas principales

#### `usuario`
Almacena las cuentas de acceso. La columna `rol_id` apunta a la tabla `rol`.

```
id | nombre | email (UNIQUE) | password (bcrypt) | activo | fecha_creacion | rol_id
```

#### `rol` y `permiso` (sistema de permisos)
Cada rol tiene un conjunto de permisos. La relacion N:N se almacena en `rol_permiso`.

```
rol: id | nombre (ADMIN/EMPLEADO)
permiso: id | nombre (enum) | descripcion
rol_permiso: rol_id | permiso_id
```

Permisos disponibles: `PRODUCTOS_CREAR`, `PRODUCTOS_EDITAR`, `PRODUCTOS_ELIMINAR`, `CATEGORIAS_GESTIONAR`, `MOVIMIENTOS_CREAR`, `VENTAS_ANULAR`, `REPORTES_VER`, `USUARIOS_GESTIONAR`.

#### `categoria` y `producto`
```
categoria: id | nombre | descripcion
producto: id | nombre | descripcion | precio | stock | stock_minimo | fecha_creacion | fecha_actualizacion | categoria_id
```
La columna `stock_minimo` permite identificar productos criticos. El metodo `isStockBajo()` en la entidad retorna `stock <= stockMinimo`.

#### `movimiento_inventario`
Registro inmutable de cada cambio de stock. No se editan ni borran movimientos.

```
id | tipo (ENTRADA/SALIDA) | cantidad | fecha | observacion | producto_id | usuario_id
```

Cada vez que se procesa una venta, el servicio crea un movimiento de tipo `SALIDA` por cada producto. Cada anulacion crea un movimiento de tipo `ENTRADA`.

#### `venta` y `detalle_venta`
```
venta: id | fecha | total | monto_pagado | cambio | metodo_pago | estado (COMPLETADA/ANULADA) | usuario_id | arqueo_id
detalle_venta: id | cantidad | precio_unitario | subtotal | producto_id | venta_id
```

`precio_unitario` en `detalle_venta` guarda el precio en el momento de la venta, preservando el precio historico aunque el producto cambie de precio despues.

#### `arqueo_caja`
```
id | fecha_apertura | fecha_cierre | monto_inicial | monto_ventas_efectivo | monto_final_esperado | monto_final_real | diferencia | observaciones | abierto | usuario_id
```

`monto_final_esperado = monto_inicial + monto_ventas_efectivo`. Solo se actualiza con ventas en EFECTIVO. Al cerrar, `diferencia = monto_final_real - monto_final_esperado`.

Un indice unico parcial garantiza que no haya dos arqueos abiertos del mismo usuario:
```sql
CREATE UNIQUE INDEX uniq_arqueo_abierto_por_usuario ON arqueo_caja (usuario_id) WHERE abierto = true;
```

## 4. Capa Backend (Spring Boot)

### Estructura de paquetes

```
EntornosProgramacion.SistemaInventario/
├── config/
│   ├── DataInitializer.java    — Siembra roles, permisos y admin al arrancar
│   ├── SecurityConfig.java     — Configura JWT, CORS, reglas de acceso
│   └── OpenApiConfig.java      — Swagger/OpenAPI
├── model/                      — Entidades JPA (@Entity)
├── repository/                 — Interfaces Spring Data JPA
├── service/                    — Logica de negocio (@Service, @Transactional)
├── controller/                 — REST endpoints (@RestController)
├── dto/
│   ├── request/                — Objetos de entrada (records Java)
│   └── response/               — Objetos de salida (records Java)
├── security/
│   ├── JwtAuthenticationFilter — Lee el token de cada request
│   ├── JwtService              — Genera y valida tokens JWT
│   └── CustomUserDetailsService — Carga usuario + rol + permisos desde BD
└── exception/
    └── GlobalExceptionHandler  — Convierte excepciones a respuestas HTTP
```

### Autenticacion con JWT

1. El usuario manda `POST /api/auth/login` con email y password.
2. `AuthService` verifica las credenciales con `BCryptPasswordEncoder`.
3. Si son correctas, `JwtService.generateToken()` crea un JWT firmado (HMAC-SHA256) con el email como `subject` y 24 horas de expiracion.
4. El frontend guarda el token en `localStorage` y lo adjunta en cada peticion via el interceptor de Axios.
5. En cada request, `JwtAuthenticationFilter` extrae el email del token, carga el usuario con `CustomUserDetailsService.loadUserByUsername()`, y pone el `Authentication` en el `SecurityContextHolder`.
6. Los endpoints con `@PreAuthorize` consultan ese contexto para verificar roles y permisos.

### Sistema de permisos

`Usuario.getAuthorities()` retorna tanto el rol como todos los permisos individuales:

```java
authorities.add(new SimpleGrantedAuthority("ROLE_ADMIN"));
// mas todos los permisos del rol:
authorities.add(new SimpleGrantedAuthority("PRODUCTOS_CREAR"));
authorities.add(new SimpleGrantedAuthority("REPORTES_VER"));
// ... etc
```

Esto permite usar tanto `@PreAuthorize("hasRole('ADMIN')")` como `@PreAuthorize("hasAuthority('VENTAS_ANULAR')")` en los endpoints.

### Transaccionalidad

Todos los metodos de servicio que modifican datos estan anotados con `@Transactional`. Esto garantiza que, por ejemplo, al procesar una venta, si falla la creacion de alguno de los movimientos de inventario, toda la operacion se revierta (rollback) y no quede el stock a medias.

### Servicios clave

#### `VentaService.procesarVenta()`
1. Valida que haya stock suficiente para TODOS los items (antes de modificar nada).
2. Calcula el total y verifica que `montoPagado >= total`.
3. Si hay `arqueoId`, verifica que el arqueo este abierto.
4. Guarda la `Venta` primero (para obtener el ID).
5. Por cada item: crea `DetalleVenta`, descuenta stock, crea `MovimientoInventario` de SALIDA.
6. Si el pago es EFECTIVO y hay arqueo, actualiza `montoVentasEfectivo` y `montoFinalEsperado`.

#### `VentaService.anularVenta()`
1. Verifica que la venta no este ya anulada.
2. Verifica que el usuario sea el dueno de la venta o ADMIN.
3. Por cada detalle: restaura el stock, crea `MovimientoInventario` de ENTRADA.
4. Si el pago fue EFECTIVO y el arqueo aun esta abierto, resta del `montoVentasEfectivo`.
5. Marca la venta como `ANULADA`.

#### `ArqueoCajaService`
- `abrirArqueo()`: Verifica que no haya otro arqueo abierto del mismo usuario (el constraint unico en BD tambien lo garantiza a nivel de datos).
- `cerrarArqueo()`: Verifica que el usuario sea el dueno o ADMIN. Calcula `diferencia = montoFinalReal - montoFinalEsperado`.

#### `ReporteService.obtenerResumen()`
Calcula todos los KPIs del dashboard en una sola llamada:
- Ventas hoy, esta semana, este mes (filtrando solo ventas COMPLETADAS).
- Ventas de los ultimos 7 dias agrupadas por dia para la grafica de barras.
- Top 5 productos por unidades vendidas en el mes.
- Diferencia promedio de los arqueos cerrados este mes.
- Ingresos por metodo de pago del mes.

#### `StockAlertService`
Tarea programada con cron `0 0 8 * * MON-SAT` (cada dia laboral a las 8 AM). Consulta todos los productos con `stock <= stock_minimo` y los registra en el log del servidor.

### Manejo de errores

El `GlobalExceptionHandler` centraliza todas las excepciones:

| Excepcion | HTTP Status | Uso |
|-----------|-------------|-----|
| `ResourceNotFoundException` | 404 | Producto, venta o usuario no encontrado |
| `BusinessException`, `IllegalArgumentException`, `IllegalStateException` | 400 | Errores de logica (stock insuficiente, monto insuficiente, arqueo ya cerrado) |
| `EmailAlreadyExistsException` | 409 | Email duplicado al crear usuario |
| `AccessDeniedException` | 403 | Sin permiso para la operacion |
| `BadCredentialsException` | 401 | Credenciales incorrectas en login |
| `Exception` (generico) | 500 | Error no controlado, se registra en el log |

    └── components/             — Toggles por rol

### Estado del servidor con TanStack Query

Cada peticion al backend se define como una `queryKey` unica:
- `["productos"]` — lista de productos
- `["productos", "stock-bajo"]` — productos bajo el minimo
- `["reportes", "resumen"]` — KPIs del dashboard
- `["arqueo", "abierto"]` — arqueo activo del usuario
- `["ventas"]` — historial de ventas

Configuracion global:
- `staleTime: 30_000` (30 segundos antes de considerar datos obsoletos)
- `retry: 1` (un solo reintento en caso de fallo)
- `refetchOnWindowFocus: false` (no recarga al volver a la pestana)

Cuando una mutacion tiene exito, invalida las queries relevantes con `queryClient.invalidateQueries()` para forzar una recarga.

### Estado local con Zustand

**useCartStore:** Maneja el carrito de compras en memoria. Al confirmar la venta, el carrito se limpia con `clearCart()`. El store persiste entre navegaciones sin recargar la pagina pero se pierde si el usuario recarga el navegador (comportamiento intencional para un POS).

**useAuthStore:** Guarda el token JWT y los datos del usuario en `localStorage` para persistir entre recargas. Al hacer logout borra ambos.

### Navegacion y guards

El router de React Router tiene tres niveles:
1. `PublicOnlyRoute`: redirige a `/` si ya esta autenticado (para `/login`)
2. `PrivateRoute`: redirige a `/login` si no esta autenticado
3. `RoleRoute`: redirige a `/` si el usuario no tiene el rol requerido (usado para `/usuarios` y `/permisos`)

### Componentes de layout

**AppLayout:** Envuelve todas las paginas autenticadas. Consulta `GET /api/productos/stock-bajo` cada 5 minutos y muestra un banner naranja si hay productos criticos.

**Sidebar:** Muestra los links de navegacion. Si hay productos con stock bajo, el link "Productos" muestra un badge rojo con el conteo.

**Topbar:** Barra superior con nombre del usuario y boton de logout.

### Cliente HTTP (Axios)

`shared/api/client.ts` configura una instancia de Axios con:
- `baseURL`: `VITE_API_URL/api` (configurable por variable de entorno)
- **Request interceptor:** lee el token de `localStorage` y lo agrega al header `Authorization: Bearer <token>` en cada peticion
- **Response interceptor:** si la respuesta es 401, hace logout automatico y redirige al login

## 6. Flujos de Negocio Completos

### Flujo: Procesar una venta en efectivo

```
Cajero navega a /carrito
    → useQuery carga productos y arqueo abierto
    → Cajero agrega 3 productos al carrito (useCartStore)
    → Carrito muestra total: $45,000
    → Cajero abre dialogo de confirmacion
    → Selecciona metodo: EFECTIVO
    → Ingresa monto recibido: $50,000
    → Sistema muestra cambio: $5,000
    → Cajero confirma

Frontend llama POST /api/ventas:
{
  items: [{productoId:1, cantidad:2}, {productoId:5, cantidad:1}],
  montoPagado: 50000,
  metodoPago: "EFECTIVO",
  arqueoId: 3
}

Backend (VentaService.procesarVenta):
1. Valida stock de producto 1 (hay 45, necesita 2 → OK)
2. Valida stock de producto 5 (hay 58, necesita 1 → OK)
3. Calcula total = 30000 + 15000 = 45000
4. Verifica cambio = 50000 - 45000 = 5000 >= 0 → OK
5. Verifica arqueo 3 esta abierto → OK
6. Guarda venta (id=9, estado=COMPLETADA)
7. Crea DetalleVenta para producto 1 (precio historico: 15000)
8. Crea DetalleVenta para producto 5 (precio historico: 28000)
9. Stock producto 1: 45 → 43, guarda MovimientoInventario SALIDA cant=2
10. Stock producto 5: 58 → 57, guarda MovimientoInventario SALIDA cant=1
11. Arqueo 3: montoVentasEfectivo 64500 + 45000 = 109500
    montoFinalEsperado = 80000 + 109500 = 189500
12. Retorna VentaResponse con todos los datos

Frontend:
→ Toast: "Venta procesada. Cambio: $5,000"
→ Limpia carrito
→ Invalida queries: productos, arqueo abierto, ventas
```

### Flujo: Cuadre de caja

```
Cajero navega a /arqueo
    → Sistema muestra: arqueo abierto desde hace 4 horas
    → Monto inicial: $80,000
    → Ventas efectivo: $109,500
    → Efectivo esperado: $189,500

Cajero cuenta el dinero fisico: $190,000
Cajero ingresa montoFinalReal: 190000 y confirma cierre

Backend (ArqueoCajaService.cerrarArqueo):
1. Verifica que el arqueo este abierto → OK
2. Verifica que el usuario sea el dueno o ADMIN → OK
3. diferencia = 190000 - 189500 = +500 (sobrante)
4. fechaCierre = ahora, abierto = false
5. Guarda arqueo

Frontend:
→ Toast: "Arqueo cerrado. Diferencia: +$500"
→ Muestra diferencia en verde (sobrante)
→ Limpia el panel de sesion activa
```

### Flujo: Anular una venta

```
Admin navega a /ventas
    → Ve la Venta #5 (Destornillador x1 = $38,000, TARJETA, COMPLETADA)
    → Hace clic en el icono de anular (Ban icon)
    → Aparece dialogo de confirmacion

Admin confirma

Backend (VentaService.anularVenta):
1. Venta #5 estado es COMPLETADA → puede anularse
2. Usuario es ADMIN → tiene permiso
3. Producto 19 (Destornillador): stock 13 + 1 = 14
4. Crea MovimientoInventario ENTRADA cant=1 obs="Anulacion Venta #5"
5. Metodo de pago es TARJETA → no afecta arqueo
6. Marca venta estado = ANULADA

Frontend:
→ Toast: "Venta #5 anulada. Stock restaurado."
→ Invalida queries: ventas, productos, arqueo abierto
→ La venta aparece tachada/opaca con badge ANULADA
```

## 7. Despliegue con Docker

El `docker-compose.yml` define tres servicios:

### `db` (PostgreSQL 16)
- Puerto: `7000:5432`
- Volumen persistente `postgres_data`
- Healthcheck con `pg_isready` para que el backend no arranque antes

### `backend` (Spring Boot)
- Imagen construida desde el `dockerfile` con Maven
- Lee variables de entorno del archivo `.env`
- `depends_on: db: condition: service_healthy`
- Puerto: `8080:8080`
- Variable `VITE_API_URL` apunta al backend dentro de la red Docker

### `frontend` (Nginx + React)
- Imagen construida desde `Dockerfile.frontend` con Node + build de Vite
- Sirve la SPA compilada con Nginx
- Puerto: `8081:8081`
- `depends_on: backend` (simple, sin healthcheck)

Todos los servicios estan en la red `inventario-network` para comunicarse por nombre de contenedor.

## 8. Decisiones de Diseno

### Por que `Long` y no `Integer` para los IDs

PostgreSQL usa `bigint` para todas las secuencias por defecto cuando Hibernate crea las tablas con `GenerationType.IDENTITY`. Si el codigo Java usa `Integer`, hay una desalineacion de tipos que puede causar errores en operaciones JPA. Se uso `Long` en todas las entidades para ser consistente con el esquema real de la BD.

### Por que guardar el precio unitario en `detalle_venta`

El precio de un producto puede cambiar en el futuro. Si solo guardaramos el `productoId`, perderiamos la informacion de cuanto costaba cuando se hizo la venta. Guardando `precioUnitario` en el detalle, el historial de ventas siempre es preciso.

### Por que EFECTIVO no afecta el arqueo cuando se usa TARJETA

El arqueo de caja representa el efectivo fisico que debe haber en la caja. Los pagos con tarjeta van directo al banco, no a la caja. Sumar esas ventas al arqueo daria una diferencia falsa.

### Por que los permisos se cargan con el rol (EAGER)

Spring Security necesita conocer todos los permisos del usuario en el momento de la autenticacion, antes de llegar a cualquier endpoint. Cargar permisos de forma lazy causaria `LazyInitializationException` fuera de una sesion de JPA. Con `FetchType.EAGER` en `Rol.permisos`, todo se carga en un solo JOIN al validar el JWT.

### Por que usar records de Java para los DTOs

Los records son inmutables, tienen constructor, getters, equals/hashCode y toString generados automaticamente. Para DTOs que solo transfieren datos (sin comportamiento), son perfectos y mas concisos que las clases tradicionales con Lombok.
